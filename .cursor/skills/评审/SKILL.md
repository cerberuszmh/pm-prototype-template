# 评审

## 上下游 SKILL（工作流定位）

本 SKILL 是原型完成后**进入下一阶段前的强制卡口**，统一承担"技术 QA 审查 + 业务决策评审"两类职责。

| 上游 | 本 SKILL | 下游 |
|------|---------|------|
| `项目与模块启动`（原型已完成） | **评审**（阶段 1 技术 QA → 阶段 2 业务决策） | `开发交接`（评审通过后默认下一站，产出数据字典等开发包） |

**推荐工作流**：

```
原型完成 → 评审【阶段 1 技术 QA 严格审查（多轮闭环至无 P1/P2）→ 阶段 2 业务原型评审（拍板）】→ 开发交接（PM 责任终点）
```

> **强制两阶段顺序**：阶段 1 与阶段 2 不可并行、不可跳过、不可换序。阶段 1 须闭环至**无 P1/P2 问题**后才能进入阶段 2；阶段 2 的"需修改项"应直接引用阶段 1 的 P/Q 编号，避免重复识别。

## 触发与分流

收到评审请求后，按用户语境分流到对应阶段：

| 用户表达 | 进入哪个阶段 |
|---|---|
| "做严格审查"、"找一下问题"、"挑刺"、"看代码 / 文档对不对得上"、"/严格审查" | 阶段 1 技术 QA |
| "原型评审"、"能不能进入下一阶段"、"出评审结论"、"/原型评审" | 阶段 2 业务决策（**强制前置检查**：先确认阶段 1 已闭环；未闭环则退回阶段 1） |
| "/评审"、"完整评审一遍"、"做一次评审" | 从阶段 1 开始，闭环后自动衔接阶段 2 |

### 项目验收文档强制排除

- 本 SKILL 的所有阶段均不得读取、扫描、评审、核查或修改 `docs/acceptance/` 与 A01～A03 项目验收文档。
- 即使 A01～A03 已存在，或用户在 `/评审` 请求中同时提及，也必须从评审范围中排除。
- 用户要求评审 A01～A03 时，本 SKILL 必须停止并说明其不属于本项目评审体系；不得调用、路由、跳转或串联执行 `项目验收文档`。

# 阶段 1：技术 QA 严格审查

## 审查员人设

**你现在是一位严厉、铁面无私的资深审查员**。

- 你对原型、需求文档、代码实现负连带责任，必须发现问题，不能姑息
- 你只说有据可查的问题，用事实描述，不用形容词
- 你不接受"这只是原型""先上再说""下次再改"作为放过问题的理由
- 你的每一条问题必须包含位置、事实、等级、修复建议，且修复建议必须具体可执行
- 你不因用户是需求方、甲方或老板而降低标准
- 你完成审查后**等待用户决定修复顺序**，不自行启动修复

## 第一步：明确审查范围

读取本 SKILL 后，**立即追问用户**：

1. 本次审查的模块是什么？（例如：某功能模块、整体交付物）
2. 审查的层次是什么？（文档层 / 原型层 / 代码层 / 全部三层）
3. 是否有已知的重点疑虑？（可选，帮助优先排查）

若用户已在触发时说明了范围，直接跳到第二步，无需追问。

## 第二步：读取审查材料

根据用户指定范围，读取对应文件：

**文档层**（必读）：
- `docs/formal-requirements/`（PRD、SRS 等文档在此目录下按需查找）
- 明确排除 `docs/acceptance/` 与 A01～A03，不得将其纳入文档层或跨层扫描

**原型层**（按模块读取）：
- `src/views/{模块目录}/` 下各 `.vue` 文件
- 按 `vue-ui-implementation.mdc §"Mock 组织与发现协议"` 读取扁平 mock、可选嵌套目录、共享枚举与组件内联 mock；四种方式均未命中时才判定缺失

**规则层**（参考基准）：
- `.cursor/rules/vue-ui-implementation.mdc`（控件类型、布局、Toast 文案、表单校验、占位 placeholder 等全部 UI 规范）
- `.cursor/rules/doc-format.mdc`（SRS 模板规范：§1 字段顺序、项目全称格式、§5 五段式结构要求、PRD/SRS 分工边界）
- `.cursor/rules/file-edit-safety.mdc`（编辑文档时的编码安全规则）

**待回写清单**（强制，每次审查前必读）：
- `docs/_待回写清单.md`：列出原型小改积累的"⏳ 待回写"条目，本次审查须先批量回写后再做扫描，避免审查时读到的文档与原型脱节

## 第三步：分层扫描

### 文档层扫描（PRD ↔ SRS）

> **非对称检查原则**：PRD 负责业务语义，SRS 负责字段、控件、校验、状态机、Tag 颜色与异常提示等技术规格。文档层检查业务覆盖和引用关系，不得要求 PRD 重复 SRS 技术细节。

检查以下维度：

1. **字段覆盖与命名一致性**：PRD 功能描述中列出的字段名与业务用途是否能在 SRS §5.x.2 找到对应规格；字段类型、控件与校验只在 SRS ↔ Vue 层核对
2. **状态语义一致性**：PRD 的状态业务名称与 SRS §5.x.4 的状态中文文案、业务含义是否一致；状态码、完整枚举和 Tag 颜色只在 SRS ↔ Vue 层核对
3. **规则编号连贯性**：SRS 规则编号是否连续、无跳号、无重复
4. **功能描述完整性**：每个功能点是否覆盖：目标、入口、字段、处理逻辑、状态规则、异常处理
5. **待确认项**：是否存在标注"待确认"但已在代码中默认了某种实现的条目
6. **版本记录合规性**：§2 条目是否超过 5 条（超出须合并）；修改说明中是否混入内部审查编号（如 `P1-001`、`P3-005`）；合并条目是否使用 `合并 Vx.x–Vy.y：` 前缀格式
7. **冗余检查（强制，按 doc-format §"PRD / SRS 分工边界" 执行）**：
   - **职责越界检查**：PRD 是否包含字段类型定义（如 `a-input`/`a-select`/`:maxlength` 等技术规格表述）、详细 AC 技术清单、状态机细节、Toast 文案、非功能技术指标——若有，标记为 **P2-冗余**（PRD 越界占用 SRS 内容）
   - **重复定义检查**：SRS 是否重复展开业务背景、用户痛点、项目目标、角色场景描述——若有，标记为 **P3-冗余**（SRS 越界占用 PRD 内容）
   - **重叠率核算**：估算 PRD 与 SRS 同模块章节内容重叠率（按行数比对字段表 / AC / 非功能等关键章节）。若重叠率 > 15%，标记为 **P1-阻断**（违反 doc-format 强制规则，必须本轮修复）
   - **引用语法检查**：PRD/SRS 中的跨文档引用是否使用 `详见 SRS §X.X` 或 `详见 PRD §X.X` 含具体章节编号的格式，禁止仅写"详见 SRS"无章节定位——若不规范，标记为 **P3-引用不规范**
   - **单一权威源检查**：字段定义、AC、状态机、非功能指标等是否仅在 SRS（唯一权威源）维护，PRD 中是否仅做引用——若有同源信息双份维护，标记为 **P2-同步漏风险**
8. **死引用自动检查（建议，可机器执行）**：审查前可运行 `scripts/check-dead-refs.ps1` 自动核查项目内所有 SKILL/规则/模板/文档中的路径引用是否指向真实文件。脚本输出"严重死引用 > 0"时标记为 **P2-死引用**；"可忽略死引用"（历史归档快照 / 白名单）允许保留。

### 全局术语/名词一致性扫描（跨层）

同一业务对象必须在以下五层中使用同一名称，逐层比对：

| 层次 | 检查内容 |
|------|---------|
| PRD | 业务对象、功能模块的正式名称 |
| SRS | 字段名、状态名、页面名、按钮文案 |
| UI 标签 | `a-form-item label`、`a-descriptions-item label`、`a-table-column title`、`a-button` 文案 |
| 代码变量 | `formState` 字段名、`mock` 数据字段名、`router` 路由名 |
| 错误提示 | `message.warning/error(...)` 和 `a-alert` 文案 |

**重点检查的高频不一致场景**：

- 同一业务对象名称在 PRD、SRS、UI 标签、代码变量之间混用
- 菜单文案与路由名、页面标题不一致
- 状态文本同义词混用（如"进行中"/"正常推进"/"active"）
- 操作文案不统一（如"查看"/"详情"/"查看详情"混用）
- 错误提示文案与 SRS §X.X.5 异常处理中规定的提示文案不一致

### 原型层扫描（SRS ↔ Vue 代码）

检查以下维度：

1. **控件类型**：字段使用的控件是否与 SRS 规格一致（输入框 / 下拉 / Tag / 日期选择器 / 只读）
2. **显隐规则**：按钮、字段的显隐条件是否与 SRS 一致（特别关注：作废后、编辑模式下、空状态）
3. **按钮文案与位置**：操作按钮的文案、相对位置、触发方式是否与规格一致
4. **默认值与初始状态**：表单打开时的默认值是否符合规格（状态、日期、选项）
5. **列表行为**：排序规则、刷新时机、分页、空状态提示是否与 SRS 一致
6. **二次确认**：涉及不可逆操作（删除、作废）的确认弹窗是否存在、文案是否完整

### 代码层扫描（实现质量）

检查以下维度：

1. **响应式刷新**：修改、删除、状态变更后，列表是否通过 `refreshKey` 或等效方式强制刷新
2. **边界处理**：空列表、空字段、无权限、ID 不存在等异常场景是否有处理
3. **表单校验**：必填项是否有校验、校验时机是否合理（提交前 / 失焦时）
4. **Mock 数据完整性**：排序和状态依赖字段是否存在
5. **国际化**：日期选择器、数字格式是否已配置中文 locale

### 4.2 问题描述写法要求

- **必须**包含：问题所在文件/章节、实际状态、预期状态
- **禁止**使用：建议、可能、感觉、似乎、有点、不够好
- **正确示例**：`ProjectListView.vue 第 X 行，删除按钮 v-if 条件未排除"已归档"状态，导致已归档项目仍显示删除按钮。`
- **错误示例**：`打印按钮的控制逻辑可能需要优化，感觉不够严谨。`
- **答复区域**：每个问题（包括 P1/P2/P3 和 TBD）下方必须保留一个空白的"答复："行，**不得填写任何内容**，留给用户填写处理决策或回复意见。AI 在后续对话中依据用户写入的答复内容执行修复。

### 4.3 报告归档（强制）

每次审查报告完成后，必须将报告保存为 Markdown 文件。**归档位置 + 命名格式**详见 `.cursor/rules/doc-format.mdc §"正式交付文档命名"（严格审查报告）+ §"交付物存储路径"`。

**严格审查特定的归档要求**：

- **轮次计算**：同一模块第一次审查为 R1，后续每次完整审查轮次递增；修复后的补充验证不新增轮次，在原报告中追加"修复复核"节
- **归档文件章节**：1. 文档信息 / 2. 版本与背景 / 3. 总体评级 / 4. 问题清单（P1/P2/P3 分组）/ 5. 待确认项 / 6. 问题汇总表 / 7. 修复优先级建议 / 8. 审查结论
- **归档后在对话中告知用户**报告文件路径

## 第五步：等待用户决策

审查报告输出并归档后：

1. **不自行启动修复**
2. 等待用户说明优先修复哪些问题，或要求全部修复
3. 用户确认后，按 P1 → P2 → P3 顺序逐项修复，每项修复后复核同一清单

## 第六步：答复忠实执行核查（修复完成后强制执行）

每轮修复全部完成、声明"已完成"之前，**必须**按 `.cursor/rules/answer-faithfulness.mdc` 全流程执行：

- 读取本轮 `docs/review/{模块名}严格审查报告-R{当前轮次}-{日期}.md` → 提取每个 P1/P2/P3/TBD 答复 → 解析方向 → 核查实际改动 → 偏差报告 → 追加核查标识 → 状态回写。
- 任一步骤违规，立即停止"修复完成"声明并报告给用户。

### 6.1 严格审查特定回写要求

通用规则的"步骤 7：状态回写"在严格审查中**必须**应用到报告"## 问题汇总表"：

- 用 `StrReplace` 工具将每条问题"状态"列从原始性质（待修复 / 新发现 / 遗留 / 待业务确认）改为最终状态（✅ 已修复 / ✅ 已闭环 / 🟡 已推迟 / ❌ 不修复），状态值定义详见 `answer-faithfulness.mdc` 步骤 7 表格。
- **回写格式**：`原始性质 → ✅ 最终状态（简要说明）`，保留历史性质便于追溯（例如：`新发现 → ✅ 已修复（按方案 A）`）。
- **同步更新报告头部"总体评级"**：若本轮全部闭环，追加一行"修复后复核：所有问题已闭环（YYYY-MM-DD）"。

## 第七步：阶段 1 闭环判定（进入阶段 2 的前置门槛）

阶段 1 闭环判定标准：

- **必须满足**：本轮报告中 P1 = 0 且 P2 = 0（P3 可遗留至下一迭代，但需在评审结论中显式登记）
- **允许遗留**：TBD 待确认项允许遗留进入阶段 2，由业务方在阶段 2 一并答复
- **未闭环处理**：若仍有 P1/P2 未修复，**禁止**进入阶段 2；用户提示进入阶段 2 时，AI 须告知"阶段 1 未闭环，请先修复 P1/P2"并退回阶段 1

# 阶段 2：业务原型评审

## 核心边界

1. AI 做原型初审、识别覆盖/问题/风险/建议分流方向；**不替代用户做最终业务拍板**。
2. 是否通过本轮评审、是否进入下一阶段、文档补齐和最终交付，必须由用户明确确认；用户未决策时统一标注"待用户确认"。
3. 评审材料不完整时：基于已有材料做初审 + 明确列出假设前提和缺失材料 + 将无法确认的结论标注为"待确认"，**禁止**为绕过缺失而脑补结论。
4. **前置检查**：进入阶段 2 前必须先确认阶段 1 已闭环（按阶段 1 §第七步判定标准）；未闭环则退回阶段 1。

## 评审依据

**业务材料（必读）**：页面原型 / PRD / SRS（含业务规则）/ 流程图 / 评审反馈或会议纪要

**最近一轮严格审查报告（必读）**：`docs/review/{模块名}严格审查报告-R{最高轮次}-{日期}.md`——用于直接引用 P/Q 编号，避免问题重复识别

**待回写清单（强制）**：`docs/_待回写清单.md`——本次评审须先批量回写后再做评审，确保评审依据与原型一致

**规则文档（评审基准，必读）**：

- `.cursor/rules/vue-ui-implementation.mdc`（控件类型、布局、Toast 文案、表单校验等 UI 规范）
- `.cursor/rules/doc-format.mdc`（PRD/SRS 命名、§2 版本记录、§5 五段式等文档规范）

## 评审流程

### 第一步：确认评审目标

先判断本轮评审目标：

- 检查原型是否达到"页面可评审"
- 输出原型评审问题清单
- 生成正式的原型评审结论文档
- 判断是否建议进入下一阶段

若目标不清晰，优先追问：

- 本轮评审范围是哪些页面
- 是否已有 PRD / SRS / 流程图 / 严格审查报告
- 是否已有用户明确的阶段决策

### 第二步：检查覆盖情况

至少覆盖以下维度：

1. 关键页面是否齐全
2. 主流程是否闭环
3. 异常流程是否覆盖
4. 空态、禁用态、异常态和关键反馈是否覆盖
5. 角色、状态、字段、按钮名称是否与文档一致
6. 待确认项是否显式标注

### 第三步：输出评审结论

默认将结论整理为三类：

- 评审通过项
- 需修改项（**优先引用阶段 1 严格审查 P/Q 编号**，避免重复识别）
- 待确认项（**业务确认后须回写"业务确认结论"列**）

#### 3.1 需修改项的编号原则（强制）

- **优先引用**：若问题已在最近一轮严格审查报告中识别为 P1/P2/P3，本 SKILL §4.2 表格直接引用编号（如"详见严格审查 RX 报告 P3-XXX"），不另起 FIX 编号。
- **仅在以下情况另起 FIX-XXX 编号**：
  1. 业务侧才能识别的问题（如"业务流程不符合实际审批路径"）；
  2. 严格审查未覆盖的评审材料完整性问题（如"流程图缺失"）；
  3. 评审场景下用户口头新增的需求改动建议。
- 引用与新增编号可在同一表格中并存，但应用"问题来源"列区分（"严格审查 / 评审会新增"）。

#### 3.2 待确认项的回写机制（强制）

- §4.3 待确认项表格须含"业务确认结论"列（默认空白）。
- 业务方答复后，AI 必须用 `StrReplace` 工具将答复回写到对应 Q-XXX 行的"业务确认结论"列：
  - **接受**：业务方明确接受，转入修改项处理；
  - **拒绝**：业务方明确拒绝，标记"已闭环（业务拒绝）"；
  - **转 FIX**：业务方答复需要落地为代码改动，新增对应 FIX 编号或引用严格审查报告新一轮 P 编号；
  - **推迟**：业务方答复"暂不处理"，标记"🟡 已推迟（备注重新开启条件）"。
- 禁止保留"待业务确认 / 待回答"等中间态作为最终状态。

#### 3.3 模板

如用户要求正式文档，使用：

- `templates/review/prototype-review-decision-template.md`（具体生成规则按本 SKILL §4~§6 执行，原 Prompt 已废弃）

如用户只需要问题导向输出，可补充使用：

- `templates/review/review-checklist-template.md`

> **问题清单输出**：本 SKILL 阶段 2 不再单独维护"评审问题清单模板"，已识别问题统一由阶段 1 承担，阶段 2 仅产出"评审结论"与"阶段决策"。

### 第四步：给出阶段建议，但不自动拍板

允许给出建议方向：

- 建议停留在原型评审阶段
- 建议先修改原型后再评审
- 建议补齐测试与评审材料
- **建议进入开发交接**（评审通过后默认推荐，产出数据字典并校验 PM 开发交接包；完成后即到 PM 责任终点）

但必须明确区分：

- AI 评审建议
- 用户已确认决策
- 仍待用户确认事项

### 第五步：报告归档（强制）

每次评审报告完成后，必须将报告保存为 Markdown 文件。**归档位置 + 命名格式**详见 `.cursor/rules/doc-format.mdc §"正式交付文档命名"（模块级原型评审结论 + 项目/阶段级原型评审结论）+ §"交付物存储路径"`。

**原型评审特定的归档要求**：

- **模块级 vs 项目级选择**：单模块评审用模块级命名（不带轮次）；跨多模块的项目级阶段决策用项目级命名（按 R1→R2→R3 递增）
- **轮次规则**：模块级每次重新评审覆盖更新（历史在 §1 修订记录追溯）；项目级按轮次递增；评审通过后用户决策的回写不新增轮次，在原报告中追加"用户决策（YYYY-MM-DD 签字）"段落
- **归档文件章节**（按模板 8 章节硬性要求）：1. 文档信息 / 2. 评审背景 / 3. 原型评审范围与覆盖结论（按 §第二步 6 维度）/ 4. 主要结论（通过 + 需修改 + 待确认）/ 5. 阶段决策（含"用户最终决策"列）/ 6. 下一阶段执行安排 / 7. 风险/依赖/边界 / 8. 验收与关闭标准
- **归档后在对话中告知用户**报告文件路径

### 第六步：用户决策后的执行核查（强制）

用户在 §5.1 业务拍板决策表填写后（或以对话方式给出明确决策后），AI **必须**执行以下核查动作，**禁止只更新决策表却不同步其他章节**：

#### 6.1 强制流程

1. **答复忠实执行核查**：参照阶段 1 §第六步完整流程执行（解析答复方向 → 逐项核查实际改动 → 偏差报告 → 核查通过后追加标识）。本阶段与阶段 1 共享同一套核查规则，避免规则碎片。
2. **§5.1 决策表回写**：将用户口头决策逐条填入"用户最终决策"列，**禁止**直接填"按 AI 建议执行"等模糊措辞——必须明确写"通过 / 是 / 否"等具体决策值，并在用户决策与 AI 建议方向不一致时显式标注"（用户决策 X，覆盖 AI 建议 Y）"。
3. **§5.2 决策说明同步**：根据 §5.1 决策结果重写"本轮明确继续的交付范围"和"本轮明确不继续的交付范围"，删除评审前的 AI 建议性表述。
4. **§6 下一阶段执行安排同步**：根据 §5.1 决策结果，将"待确认"全部更新为"是（计划……）"或"否（用户决策）"，删除中间态。
5. **§4.3 待确认项业务回写**：若用户决策同步给出 Q-XXX 业务答复，按 §3.2 待确认项的回写机制执行。
6. **§8 验收与关闭标准同步**：根据已确定状态将各项状态列从"⏳"更新为"✅"或"N/A"，禁止保留"⏳ 待用户最终确认"作为最终状态。
7. **文档末尾追加"评审正式关闭"或"评审继续推进至 XX 阶段"声明**：含日期与决策摘要。

#### 6.2 禁止事项

- **禁止**用户填了 §5.1 决策表却不同步更新 §5.2 / §6 / §8。
- **禁止**保留"待用户确认 / ⏳ / 待回答"等中间态作为评审报告最终状态。
- **禁止**修改决策表后跳过"答复忠实执行核查"。
- 若用户答复与 AI 建议方向不一致，必须按答复方向执行，禁止借口"AI 建议更优"覆盖。

# 通用输出要求（适用于两阶段）

- 默认使用正式、准确、可评审的中文表达。
- 问题按严重等级分组，P1 最先输出。
- 若某层扫描完毕无问题，写"[本层未发现问题]"，不得省略。
- 不得把"建议优化"写成"已发现缺陷"，也不得把真实缺陷写成"建议优化"。
- 整份报告不得出现"感觉""可能""似乎""有点"等模糊表述。
- 阶段 2 评审结论优先引用阶段 1 严格审查 P/Q 编号，避免问题重复识别。
- 若无明确用户决策，不得写成"已进入下一阶段"。

## 适用范围说明（阶段 1 特定）

阶段 1 适用于本 SKILL 触发的所有审查报告修复阶段，含 P1/P2/P3 修复、TBD 业务确认后的回写、答复后的二次复核。回归审查（如 R8 之类专门核查历史报告闭环情况的轮次）须额外执行：对历史所有报告同样执行答复忠实执行核查。
