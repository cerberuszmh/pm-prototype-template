# 需求变更

## 上下游 SKILL（工作流定位）

本 SKILL 在项目工作流中处于**变更入口**，可在任意阶段触发。变更分析后会**回退**到对应阶段对应 SKILL 处理。

| 上游 | 本 SKILL | 下游（按变更回退阶段判断） |
|------|---------|------------------------|
| 任意阶段（来自客户/用户的变更请求） | **需求变更**（结构化变更 + 影响分析 + 回退建议） | `项目与模块启动`（变更影响底稿/PRD/SRS/原型）/ `文档生成与版本管理`（仅文档版本升级）/ `评审`（变更落地后阶段 1 严格审查 + 阶段 2 原型评审） |

**典型工作流**：

```
变更请求 → 需求变更（生成变更说明 + 回退建议）→ 用户确认 → 回退到对应阶段对应 SKILL → 严格审查 → 原型评审
```

## 核心原则

1. 收到变更后，不直接修改正式交付物，先形成《需求变更说明》。
2. 先做需求清洗、归类、去重和冲突识别，再判断影响范围。
3. 必须明确本次变更属于新增、修改、删除还是待确认事项。
4. 必须判断变更影响哪些交付物，以及建议回退到哪个阶段处理。
5. 对未确认信息统一标注“待确认”，不得擅自编造业务事实。

## 执行流程

### 第零步：区分 FB（快速轨反馈）与 CR（正式变更）

收到改动诉求时先判断模块所处轨道，避免对尚无正式文档的模块误启 CR 状态机：

| 模块状态 | 机制 | 编号与落点 |
| --- | --- | --- |
| 双速轨快速轨中（尚无正式 PRD/SRS） | **反馈迭代**，不启动本 SKILL 的 CR 状态机 | `FB-XXX` 记入轻量需求摘要 §8 迭代记录，由 `项目与模块启动` SKILL §2.8 DT-F3 处理 |
| 方向确认后、正式 PRD 未产出前 | 仍算快速轨收尾；改方向回到 DT-F3，不必 CR | 同上 |
| 正式 PRD/SRS 已存在（文档先行档，或双速轨正式轨） | 走本 SKILL 完整 CR 状态机 | `CR-XXX` 记入 `docs/changes/{模块名}变更记录.md` |

### 第一步：确认变更输入

优先收集以下材料：

- 客户原始诉求
- 会议纪要或沟通记录
- 截图、草图、页面修改意见
- 当前相关 PRD / SRS / 流程图 / 页面原型

如果材料零散，可先按原文整理，不要求用户先写成正式需求语言。

### 第二步：先生成变更说明

默认基于以下模板与本 SKILL 自身约束生成：

- 模板：`templates/requirements/requirement-change-template.md`

输出时至少明确：

- 变更编号（CR-XXX，详见下方"变更编号管理"）
- 变更背景
- 变更点清单
- 待确认问题
- 影响范围判断
- 受影响交付物
- 回退阶段建议

### 变更编号管理（强制）

**编号格式**：`CR-{NNN}`，三位数字递增，如 `CR-001`、`CR-002`、`CR-015`。

**编号规则**：

- 同一模块内编号在《XX 模块变更记录》中递增；
- 项目级跨模块变更采用单独前缀 `CR-PROJ-{NNN}`；
- 编号一旦分配不可复用；若变更被驳回，标记状态为"已撤销"但保留编号占位。

**变更状态机**（每条变更必须显式标注当前状态）：

| 状态值 | 含义 | 转移条件 |
|------|------|---------|
| `提交` | 变更刚记录，未分析 | 默认初始状态 |
| `评估中` | 正在做影响分析 | AI 完成 §第三/四步分析后 |
| `已批准` | 用户确认接受变更 | 用户答复"接受/确认执行" |
| `已驳回` | 用户决定不接受 | 用户答复"不确认/驳回" |
| `执行中` | 已分发到下游 SKILL 处理 | 已批准 + 已分流到对应 SKILL |
| `已完成` | 所有受影响交付物均已更新 | 下游 SKILL 完成且通过答复忠实执行核查 |
| `已撤销` | 历史变更被后续变更取消 | 后续变更明确撤销该条 |

### 报告归档（强制）

变更记录采用**追加式归档**：单一文件维护本模块所有 CR 条目。**归档位置 + 命名格式**详见 `.cursor/rules/doc-format.mdc §"正式交付文档命名"（需求变更记录）+ §"交付物存储路径"`。

**需求变更特定的归档要求**：

- 每条变更以 `## CR-{NNN}` 二级标题分节
- 文档头部必须含本模块的"变更状态汇总表"（编号 / 提交日期 / 状态 / 变更摘要 / 受影响交付物 5 列）
- 每个 CR-XXX 节必须含：变更背景 / 变更点清单 / 影响范围判断 / 回退阶段建议 / 用户决策（留白栏）/ 执行记录（修复完成后回写）
- 若 `docs/changes/` 目录不存在，执行前用 `New-Item -ItemType Directory -Force -Path "docs/changes"` 先创建
- **归档后在对话中告知用户**变更编号和归档路径

> 完整的变更记录文件结构示例详见 `templates/requirements/requirement-change-template.md`（追加式版本）。

### 第三步：判断影响范围

至少检查以下方面是否受影响：

1. 项目目标
2. 本期范围
3. 角色权限
4. 业务流程
5. 状态规则
6. 页面原型
7. 测试用例与使用说明书

如果影响多个交付物，必须逐项说明是否需要更新，而不是笼统写“有影响”。

### 第四步：判断回退阶段

根据变更性质给出回退建议：

- 项目定位或系统级需求结构变了：回退到产品发现
- 项目范围、术语或模块编号变了：回退到 P07 §9~§12 对齐决策段
- 模块功能范围变了：回退到模块 PRD
- 规则、字段、权限、状态变了：回退到 SRS
- 业务流转变了：回退到流程设计
- 页面结构、交互、状态展示变了：回退到页面原型
- 双速轨正式轨中页面结构、交互变了：回退到「双速轨-正式原型」（`项目与模块启动` SKILL §2.8 DT-R4）；快速轨中的改动不走本表，按第零步以 FB 处理
- 仅影响验证与覆盖范围：回退到测试补充

必须同时写清：

- 建议回退阶段
- 判断依据
- 若不回退的风险

### 第五步：等待确认后再推进更新

在用户确认前：

- 可以给出影响分析和处理建议
- 可以给出推荐修改顺序
- 不能默认直接改完整套正式文档或原型

若用户明确要求继续更新，再按确认范围推进对应交付物。

**移交边界（强制）**：
- 若变更涉及 PRD / SRS / 流程图 / 原型实质性内容修改，**必须移交 `文档生成与版本管理` SKILL** 执行升版与版本记录条目生成；本 SKILL 仅维护变更记录文件本身（`docs/changes/{模块名}变更记录.md`）。
- 若变更影响原型代码或 Mock 数据，移交 `项目与模块启动` SKILL 阶段五重新生成原型；本 SKILL 不直接改 `.vue` 文件。
- 若变更落地后须复核全项目一致性，移交 `评审` SKILL 阶段 1 启动新一轮 R{n+1} 严格审查。
- **PM 变更闭环上限**：受影响交付物更新并按需重走两阶段评审后，可进入开发交接；不得默认继续接口对齐、生产构建、数据库、联调或部署。

### 第六步：用户决策后的执行核查（强制）

用户对变更说明给出"接受/驳回/部分接受"决策后，**必须**按 `.cursor/rules/answer-faithfulness.mdc` 全流程执行答复忠实执行核查：

- 读取 `docs/changes/{模块名}变更记录.md` → 提取用户答复 → 解析方向 → 核查实际改动是否到位 → 偏差报告 → 追加核查标识 → 状态回写。
- **强制状态回写**：将变更条目状态从"评估中" → "已批准/已驳回/已撤销/已完成"，并在"执行记录"小节追加"修复执行清单"+"答复忠实执行核查：通过（共 N 项）"。
- 任一步骤违规，立即停止"已完成"声明并报告给用户。

## 输出要求

- 默认使用正式、准确、可评审的中文表达。
- 先写变更结论，再写影响分析与处理建议。
- 对“确认执行 / 不确认执行 / 部分确认”必须单独成节。
- 明确区分：
  - 已确认纳入本次变更的内容
  - 建议暂不纳入的内容
  - 待确认内容
- 不得把“建议回退”写成“已经回退执行”。

- `templates/requirements/requirement-change-template.md`

- `.cursor/rules/answer-faithfulness.mdc`（用户决策后的强制核查流程）
