# 产品发现

## 上下游 SKILL（工作流定位）

本 SKILL 是**项目级首次启动**时，介于"启动输入收集"与"P07 合并版项目级 PRD"之间的发现（Discovery）阶段，负责把模糊、分散、大量的原始素材收敛为可落地的系统级结构化成果。

| 上游 | 本 SKILL | 下游 |
|------|---------|------|
| `项目与模块启动`（项目级启动，完成启动输入收集） | **产品发现**（素材提炼 → 需求地图 → JTBD → 用户旅程图 → 功能模块 → IA） | `项目与模块启动`（回到 P07 对齐决策段与骨架 → 模块 PRD → SRS → 原型） |

**推荐工作流**：

```
项目总入口 → 项目与模块启动（项目级，启动输入收集）→ 产品发现（本 SKILL，按档位产出系统级成果）→ P07 对齐决策段与骨架 → 模块 PRD → SRS → 流程图 → 原型
```

## 核心原则

1. **仅项目级一次性触发**：产品发现只在"项目级首次启动"执行一次，产出**系统级**成果（全系统各一份）。**模块级新增功能不重做产品发现**，直接引用本阶段产出的需求地图 / JTBD / IA 等成果。
2. **系统级粒度**：6 件套均为整个系统一份，不按模块拆分。命名统一使用 `P{nn}-{系统名}` 双层前缀（`P01-` ~ `P06-` 由 `doc-format.mdc` 强制固定分配；`{系统名}` 取自全局系统名称，与 `src/layouts/WorkspaceLayout.vue` 的系统名称同源）。
3. **顺序约束**：素材提炼 → 需求地图 → JTBD → 用户旅程图 → 功能模块 → IA，**不得跳步**（中 / 轻档裁剪规则见 §1.2，被裁剪的阶段直接跳过；保留执行的阶段顺序不变）。
4. **来源可追溯（强制）**：每一层产出物的每个条目必须带"来源 ID"列，回链到上一层条目，形成 `M- → RM- → JTBD- → UJ- → F- → IA-` 的完整链路，保证最终功能能回溯到原始素材的哪句话。
5. **价值取舍显式化**：第 0 步必须按价值评分标准对原始信息做"纳入 / 降级 / 拆解 / 丢弃"裁决，噪声**留痕不删**，可复核。
6. **不脑补**：无法确认的业务事实统一标注"⚠️ 待确认"，禁止编造。
7. **检查点强制停止**：每个子阶段输出"🛑 已停止"检查点后必须结束本次回复，下一阶段须等用户在新一轮对话中确认。

## 术语释义（首次出现处统一口径）

| 术语 | 中文口径 | 含义 |
|---|---|---|
| 需求地图（Requirement Map） | 需求地图 | 把全部清洗后的需求按多级主题铺成的全景结构 |
| JTBD（Jobs To Be Done） | 用户任务 | 用户"雇用"本系统去完成的核心任务及其动机 |
| 用户旅程图（User Journey Map） | 用户旅程图 | 用户为达成目标所经历的阶段、触点、行为、痛点、情绪 |
| 信息架构（IA, Information Architecture） | 信息架构 | 系统的导航 / 页面层级组织结构 |

## 第一步：触发与适用范围确认

### 1.1 范围识别（强制前置判断）

| 范围类型 | 触发特征 | 处理 |
|---------|---------|------|
| **项目级首次启动** | 项目尚无系统级产品发现成果（`docs/discovery/` 为空或缺件） | 执行本 SKILL，产出系统级 6 件套 |
| **模块级新增** | 项目已完成产品发现，仅新增某个功能模块 | **不触发本 SKILL**；回到 `项目与模块启动`，引用已有产品发现成果与 P07，从该模块 PRD（二件套首件）开始 |

**强制识别问句（执行前必须问）**：

> 本项目是否已做过产品发现（`docs/discovery/` 是否已有需求地图 / IA 等成果）？
> - 否 → 继续本 SKILL（项目级首次启动）
> - 是 → 终止本 SKILL，提示用户走模块级流程（`项目与模块启动`），引用已有成果

### 1.2 档位判定（三档分级）

| 档位 | 适用场景 | 执行范围 |
|---|---|---|
| **重档** | C 端 / 多角色对外、多触点、流程分叉多、原始素材杂 | 0~5 全部 6 个子阶段 |
| **中档**（默认） | 内部 B 端工具型系统、少量外部用户、Web 为主 + 邮件/短信通知、流程数 2~4 条 | P01 素材提炼 + P05 功能模块 + P06 IA 三件必做；P02 需求地图与 P05 合并；P03 JTBD 简化为角色-任务对照表；P04 用户旅程图跳过 |
| **轻档** | 极简单功能 / 单角色 CRUD 工具 / 素材仅一份口述 | P01 素材提炼（仅 3 档评分）+ P05 功能模块 + P06 IA 三件套；P02 / P03 / P04 全跳过 |

> 默认按**中档**起步。重 / 轻档需依据 §1.2.1 评分结果或用户显式指定切换。所有档位均必须按 §1.3 完成档位确认后方可进入 §3.0 素材提炼。

### 1.2.1 5 维评分判定标准（强制）

档位判定按以下 5 维度二选一打分，**总分映射档位**：

| 维度 | 重档信号（2 分） | 中档信号（1 分） | 轻档信号（0 分） |
|---|---|---|---|
| **D1 用户面向** | C 端 / 多角色对外（≥3 类外部用户） | B 端内部 + 少量外部（1~2 类外部用户） | 纯内部工具，1 类用户 |
| **D2 触点复杂度** | 跨渠道（APP / Web / 邮件 / 客服 / 线下 ≥3 触点） | 单 Web 端为主 + 邮件 / 短信通知 | 单 Web 端，无外部通知 |
| **D3 业务流程数** | 主流程 ≥5 条且互相分叉 | 主流程 2~4 条 | 单一主流程（CRUD 类） |
| **D4 原始素材体量** | 调研对话 / 讲话 / 纪要 ≥10 篇，矛盾多 | 3~9 篇，少量矛盾 | ≤2 篇或仅一份需求口述 |
| **D5 角色协作复杂度** | 角色间存在审批 / 流转 / 协同闭环 | 角色间仅数据传递 | 单角色独立操作 |

**总分映射**：

- **8~10 分 → 重档**
- **3~7 分 → 中档**
- **0~2 分 → 轻档**

> 评分过程必须落到回复正文中，禁止只给出结论不给依据。每一维必须明确标注 0 / 1 / 2 分及理由。

### 1.3 档位触发方式

档位确认有三种触发方式，**进入 §3.0 素材提炼前必须完成档位确认**：

#### 方式 A：用户主动声明（最高优先级）

用户在调用产品发现时一句话定档（自然语言或带后缀均可）：

- "按重档走全套 6 件套"
- "按中档走，跳过 JTBD 和用户旅程图"
- "按轻档走，只要素材提炼 + 功能模块 + IA"

接收到声明后，AI 仍需按 §1.2.1 给出 5 维评分作为「审查提示」留痕，**但执行档位以用户声明为准**。

#### 方式 B：Cursor 初判 + 用户确认（默认）

若用户未声明档位，AI 进入产品发现后必须先执行档位判定流程，输出固定格式问句并停止：

```
进入产品发现前，先确认档位。

【5 维评分】
- D1 用户面向：xxx → x 分
- D2 触点复杂度：xxx → x 分
- D3 业务流程数：xxx → x 分
- D4 原始素材体量：xxx → x 分
- D5 角色协作复杂度：xxx → x 分
合计 x 分 → 初判【x 档】

【x 档执行范围】
✅ P01 素材提炼（xxx）
{各阶段执行 / 跳过 / 简化标注}

是否确认按【x 档】执行？或要切换到【其他档位】？

🛑 已停止，等待档位确认。
```

用户回复 "确认" 或显式改档后方可进入 §3.0。

#### 方式 C：冲突兜底（强制约束）

| 情形 | 处理 |
|---|---|
| 用户声明档位 ≠ Cursor 初判档位 | 以**用户声明**为准；AI 必须在执行前列出 5 维评分作为「审查提示」留痕，不得沉默放行 |
| 5 维评分落在档位边界（如恰好 7 分或 3 分） | 默认按**较低档位**（更精简）起步；若执行到 §3.4 功能模块时发现规模超预期，停下来追加「档位升级提示」，让用户选是否补做 P03 / P04 |
| 执行中用户临时改档 | 已完成阶段**不重做**；后续阶段按新档位执行；在 P05 末尾追加「档位变更记录」段落 |

## 第二步：来源 ID 链规范（强制）

各层条目编号与来源回链规则如下，所有模板均含"来源 ID"列：

| 层 | 子阶段 | 条目前缀 | 来源指向 |
|---|---|---|---|
| 0 | 素材提炼 | `M-001` 素材原子 | 原始材料编号 + 出处定位 |
| 1 | 需求地图 | `RM-001` 地图节点 | 来源 `M-xxx` |
| 2 | JTBD | `JTBD-001` | 来源 `RM-xxx` |
| 3 | 用户旅程图 | `UJ-001` 触点 | 来源 `JTBD-xxx` |
| 4 | 功能模块 | `F-001` 功能点 | 来源 `UJ-xxx` / `JTBD-xxx` |
| 5 | 信息架构 | `IA-001` 节点 | 来源 `F-xxx` |

## 第三步：六个子阶段

### 3.0 子阶段 0：素材提炼与价值取舍（去噪）

**本阶段档位差异**：

| 档位 | 执行方式 |
|---|---|
| 重档 | 5 维价值评分 + 4 类区分 + ✅🟡⚠️❌ 四种裁决 + 留痕 |
| 中档 | **3 档评分**（✅ 纳入 / 🟡 降级 / ❌ 丢弃，去掉⚠️ 拆解归入纳入）+ 4 类区分 + 留痕 |
| 轻档 | **仅 3 档评分**，4 类区分不强制，留痕保留 |

**目标**：把模糊、分散、大量的原始素材切成"信息原子"，按价值评分裁决去留，输出干净的需求条目，喂给需求地图。

**模板**：`templates/requirements/material-distillation-template.md`
**产出物**：《P01-{系统名}素材提炼与价值取舍》（归档 `docs/discovery/P01-{系统名}素材提炼与价值取舍.md`）

**强制动作**：
- **原子切片**：把每段对话 / 讲话 / 纪要切成独立信息原子（`M-xxx`），每条锚定来源材料与出处。
- **四类区分**（重 / 中档强制，轻档可选）：每个原子标注 用户原话 / 真实需求 / 方案建议 / 待确认事项（沿用现有底稿四类口径）。
- **价值评分**：重档按 5 维度（业务价值 / 真实性 / 共识度 / 来源权重 / 可落地性）；中 / 轻档按 3 档简化（直接给出 ✅ / 🟡 / ❌）。
- **裁决**：重档 ✅ 纳入 / 🟡 降级 / ⚠️ 拆解 / ❌ 丢弃；中 / 轻档 ✅ 纳入 / 🟡 降级 / ❌ 丢弃。噪声**留痕不删**，可复核。

**🛑 检查点**（见 §第四步格式）后停止。

### 3.2 子阶段 2：JTBD（用户任务）

**本阶段档位差异**：

| 档位 | 执行方式 |
|---|---|
| 重档 | 完整 "当【情境】时，用户想要【动机】，以便【预期结果】" 公式 |

**强制动作**：

- 中档：角色-任务对照表，每行 `JTBD-xxx` / 角色 / 一句话任务 / 来源 / 优先级，不强求三段式表达。

**🛑 检查点**后停止。

### 3.3 子阶段 3：用户旅程图

**本阶段档位差异**：

| 档位 | 执行方式 |
|---|---|
| 重档 | 按角色 / 核心目标分条旅程，每条拆"阶段 → 触点 → 用户行为 → 痛点 → 情绪 → 机会点" |
| 中档 | **跳过**；痛点直接挂到 §3.4 P05 功能点的「来源说明」字段下，不再独立画旅程 |
| 轻档 | 跳过 |

> **判别提示**：用户旅程图主要价值在 C 端多触点、情绪起伏大、流失率高的产品。B 端内部工具型系统（如本项目这类报名/审核/管理后台）旅程多为线性 CRUD，35 个触点最终会收敛回功能点，中间翻译损耗大于增益，**中档以下默认跳过**。

**目标**：基于 JTBD + 角色，描绘用户达成目标的全过程，**用旅程痛点驱动后续功能发现**。

**模板**：`templates/design/user-journey-template.md`
**产出物**：《P04-{系统名}用户旅程图》（归档 `docs/discovery/P04-{系统名}用户旅程图.md`）；中档与轻档**不产出**

**强制动作**（仅重档执行）：
- 按角色 / 核心目标分条旅程；每条旅程拆"阶段 → 触点 → 用户行为 → 痛点 → 情绪 → 机会点"。
- 每个触点（`UJ-xxx`）带来源 `JTBD-xxx`；机会点标注"可能催生的功能方向"。

**🛑 检查点**后停止。

### 3.4 子阶段 4：功能模块清单

**本阶段档位差异**：

| 档位 | 执行方式 |
|---|---|
| 重档 | 一级模块 → 二级子模块 → `F-xxx`，每个功能点来源 `UJ-xxx` / `JTBD-xxx` |
| 中档 | 同重档结构，但功能点来源链回退为 `JTBD-xxx` 或直接 `M-xxx`（因 P04 已跳过、P02 已并入本阶段），允许在一级模块层并入原本属于 P02 的主题树 |
| 轻档 | 同中档，但来源链允许仅写 `M-xxx`（因 P02 / P03 / P04 均跳过） |

> **三档共同要求**：本阶段是产品发现的核心产出之一，结构粒度与功能完整性**不缩减**，仅缩减的是来源链上溯路径。

**目标**：由旅程触点 / 痛点和 JTBD 聚类，输出多级功能模块与功能点。

**模板**：`templates/requirements/feature-breakdown-template.md`
**产出物**：《P05-{系统名}功能模块清单》（归档 `docs/discovery/P05-{系统名}功能模块清单.md`）

**强制动作**：
- 多级结构：一级模块 → 二级子模块 → 功能点（`F-xxx`），每个功能点带来源链（重档 `UJ-xxx` / `JTBD-xxx`，中档 `JTBD-xxx` / `M-xxx`，轻档 `M-xxx`）。
- 标注优先级与本期 / 非本期范围初判。
- 本清单即**后续模块级启动的拆分依据**。

**🛑 检查点**后停止。

### 3.5 子阶段 5：信息架构（IA）

**本阶段档位差异**：

| 档位 | 执行方式 |
|---|---|
| 重档 | 完整页面层级树 + 页面类型 + `F-xxx` 映射 |
| 中档 | 同重档（这是核心产出，不缩） |
| 轻档 | 同重档（这是核心产出，不缩） |

> **三档共同要求**：IA 是原型的直接输入，**任何档位均不得缩减**。

**目标**：把功能组织成系统的导航 / 页面层级结构，作为原型页面的直接输入。

**模板**：`templates/design/information-architecture-template.md`
**产出物**：《P06-{系统名}信息架构（IA）》（归档 `docs/discovery/P06-{系统名}信息架构（IA）.md`）

**强制动作**：
- 导航 / 页面层级树（`IA-xxx`），每个页面节点映射到功能 `F-xxx`。
- 标注页面类型（列表 / 详情 / 表单 / 弹窗等）与层级关系。

**🛑 检查点**后停止；本阶段完成即产品发现结束，建议回到 `项目与模块启动` 进入 **P07 对齐决策段（§9~§12）→ 项目级 PRD 骨架版**（节奏详见 `doc-format.mdc §"项目级 PRD 两阶段节奏"`）。

## 第四步：从指定阶段进入

若用户已有某些产出物（如"我已有需求地图，直接做 JTBD"），允许从指定子阶段进入：

- 先按 §1.1 确认仍属项目级；
- 核查指定阶段的**上游产出物是否已存在且可用**（缺失则提示先补上游）；
- 从该子阶段继续，沿用既有来源 ID 链。

## 第五步：阶段决策检查点（强制停止）

每个子阶段结束后，必须输出以下检查点并立即停止：

```
【子阶段完成】{子阶段名称} 已完成
档位：{重档 / 中档 / 轻档}
交付物：{文件路径}
来源链核对：{本阶段条目是否全部回链上游，N/N}
待确认项：{n 项，见文档末尾}
建议下一步：进入【{下一子阶段 / P07 对齐决策段与骨架版}】

🛑 已停止。请确认后告知是否继续。
```

## 第六步：用户决策后的执行核查（强制）

用户给出决策（含档位确认、阶段推进确认、终止决策等）后，必须按 `.cursor/rules/answer-faithfulness.mdc` 全流程执行：

- 读取本轮产出 → 提取答复 → 解析方向 → 核查改动 → 偏差报告 → 追加核查标识 → 状态回写。
- 任一步骤违规，立即停止"已完成"声明并报告给用户。

## 第七步：执行中改档处理（强制）

用户在产品发现执行过程中临时调整档位（如从中档升为重档、或从重档降为中档），按以下规则处理：

1. **已完成阶段不重做**：已落档案的 P01 / P02 / P03 / P04 / P05 / P06 不回溯重写，不删除，不降级。
2. **后续阶段按新档位执行**：从当前未开始的子阶段起，严格按新档位的范围与精简规则执行。
3. **变更记录强制留痕**：在 P05 功能模块清单末尾追加「档位变更记录」段落，格式：

   ```
   ## 档位变更记录
   
   | 时间 | 变更前档位 | 变更后档位 | 变更原因 | 已完成阶段 | 后续受影响阶段 |
   |---|---|---|---|---|---|
   | YYYY-MM-DD | 中档 | 重档 | 用户决定补做 P04 用户旅程图 | P01 / P05 / P06 | 新增 P04 |
   ```

4. **降档触发数据保留约定**：若从重档降为中档 / 轻档，已产出的 P02 / P03 / P04 保留在 `docs/discovery/`，不删除；但下游 PRD / SRS 引用时**以新档位为准**，不强制回链已被跳过的层级。
5. **不允许"重档体感的中档"**：禁止口头声明中档却实际按重档执行；档位是机械范围约束，不是工作量软指标。

## 输出要求

- 使用正式、准确、可评审的中文。
- 术语、角色、状态名、字段名全局统一，与下游 PRD / SRS / 原型一致。
- 每份产出物均含"来源 ID"列，禁止出现无来源的凭空条目。
- 待确认事项统一标注 ⚠️，不脑补业务事实。
- 不得把"建议继续"写成"已经继续执行"。
