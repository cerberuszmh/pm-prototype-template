# 项目与模块启动

## 上下游 SKILL（工作流定位）

本 SKILL 是**项目工作流的起点**，覆盖"从 0 推进到原型"的全部阶段。


| 上游            | 本 SKILL                             | 下游                                         |
| ------------- | ----------------------------------- | ------------------------------------------ |
| `项目总入口`（路由分流） | **项目与模块启动**（产品发现/P07 定锚 → 模块 PRD → SRS → 流程图 → 原型） | `评审`（阶段 1 严格审查多轮 R1→Rn 闭环 → 阶段 2 原型评审业务决策） |


**推荐工作流**：

```
项目总入口 → 项目与模块启动【项目级：产品发现 → P07 合并版 PRD；模块级：PRD → SRS → 流程图 → 原型】→ 评审【阶段 1 严格审查 → 阶段 2 原型评审】→ 开发交接（PM 责任终点）
```

**适用范围说明**：

- 本 SKILL 同时覆盖"项目级首次启动"与"项目内新功能模块启动"两类场景：项目级先完成产品发现与 P07 定锚，模块级直接进入 PRD/SRS 二件套。本 SKILL §3.1 覆盖范围识别。

## 核心原则

1. **顺序约束**：启动输入 →（项目级）产品发现 → P07 对齐决策段与骨架 →（模块级）PRD → SRS → 流程图 → 原型，**不得跳步**（详见 §2.1；产品发现仅项目级首次启动执行，模块级新增不重做）。
2. **每阶段有交付物**：每个阶段必须产出对应文档，经过用户确认后再进入下一阶段。
3. **术语先行**：在 P07 §10 术语口径与模块 PRD 起草阶段确认角色名称、状态名称、字段名称、模块名称，后续所有文档和原型必须复用。
4. **待确认显式标注**：不确定的业务事实统一标注"待确认"，不编造业务事实。
5. **PM 边界明确**：完整 PM 模块流程默认推进到开发交接；用户可在原型评审检查点提前停止，不自动进入接口对齐、生产构建、数据库、联调或部署。
6. **检查点强制停止**：每阶段输出"🛑 已停止"检查点后必须结束本次回复，下一阶段须等用户在新一轮对话中确认。
7. **已存在的交付物直接跳过，不重新生成**：先按 §3.2 跳过条件判定标准核查，再决定跳过还是推进。



## 第一步：识别范围与目标



### 1.1 范围识别（项目级 vs 模块级）


| 范围类型        | 触发特征                                    | 调整点                                                                                                                                                                                                                                                                              |
| ----------- | --------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **项目级首次启动** | 项目目录尚无 PRD/SRS、用户描述"新项目"或"从 0"          | 必须从"启动输入收集"开始；**产出合并版项目级 PRD**（`P07-{系统名}产品需求文档（PRD）.md`，单一文件承担原"项目对齐稿 + 项目级 PRD"双重职责：已确认决策表 / 术语口径 / 模块编号固定 / 非功能需求 / 权限模型 / 验收里程碑 / 模块依赖矩阵），**两阶段节奏产出**（骨架 → 滚动回填 → 封板，详见 `doc-format.mdc §"项目级 PRD 两阶段节奏"`）                                                                   |
| **模块级新启动**  | 项目已有项目级 PRD，但当前模块无对应模块级 PRD/SRS         | 可跳过"启动输入收集"，**直接从模块级 PRD 开始（二件套：PRD + SRS，不再单独产出 M{n}-01 底稿）**；模块编号 `{n}` 以 P07 §11 为准，文件形如 `docs/formal-requirements/M{n}-02-{模块名}模块产品需求文档（PRD）.md`；模块级 PRD 必须**引用项目级 PRD**，禁止重复项目级背景 / 非功能 / 权限 / 里程碑；需求背景 / 角色概述 / 待确认清单嵌入 PRD 对应章节 |
| **老系统翻新模式** | 用户提及"翻新/旧系统改造/老系统迁移/基于老系统重做"，或提供老系统访问地址 | 走本 SKILL §2.3-翻新完成老系统盘点与翻新决策；确认后回到 §2.4 模块 PRD                                                                                                                                                                                                                              |


**产品发现衔接（项目级 vs 模块级，强制）**：

- **项目级首次启动**：完成"启动输入收集"后，须先转交 `产品发现` SKILL 产出相应档位的系统级成果，再回到本 SKILL 生成 P07 对齐决策段与骨架。
- **模块级新增**：不重做产品发现，直接引用项目级成果与 P07，从该模块 PRD 开始。

**翻新模式的强制识别问句（在执行阶段一前必须问）**：

> 本模块在老系统是否已有对应实现？
>
> - 是 → 进入本 SKILL §2.3-翻新 子流程由其执行阶段一替代
> - 否 → 继续本 SKILL 走全新模块流程（二件套 PRD + SRS）

### 1.3 目标节点确认（关键，决定推进范围）

若用户未明确，优先追问本轮停止节点：


| 选项         | 含义                       |
| ---------- | ------------------------ |
| 开发交接为止（默认） | 完成原型、两阶段评审与开发交接，在 PM 责任终点停止 |
| 原型评审为止     | 完成两阶段评审并记录业务决策，不生成开发包       |
| 仅补齐指定文档    | 只处理用户点名的 PRD / SRS / 流程文档       |


**默认值**：若不确定，按"开发交接为止"作为 PM 完整目标，但仍须遵守每阶段检查点逐步确认，不在同一轮连续输出全套交付物。

## 第二步：按链路推进（8 步，含项目级产品发现衔接步与 1 个翻新替代步骤）

> **模块级二件套（强制，自本版起对新模块生效）**：
>
> 自本规则更新起，**新启动**的模块级文档默认采用「PRD + SRS」二件套，**不再单独产出 M{n}-01 结构化需求底稿**——原底稿承担的"需求背景 / 角色权限概述 / 待确认清单"职责直接嵌入 M{n}-02 PRD 的 §"需求背景"章节。
>
> **兼容范围**：
>
> - 已存在的 `M{n}-01-{模块名}结构化需求底稿.md` 文件（如 M4-01、M7-01）保留不动，作为历史交付物。
> - **老系统翻新模块**仍按 §2.3-翻新 子流程产出 `M{n}-01-{模块名}模块老系统盘点与翻新决策.md`，因其 4 表内容（功能清单 / 翻新决策 / 术语映射 / 待业务决策）不可被 PRD 替代。
> - 全新模块直接跳到 §2.4 阶段二 PRD（按本节"二件套"要求嵌入需求背景）。

### 2.3 历史兼容：结构化需求底稿（**已废弃，不进入新项目活动流程**）

> ⚠️ **本阶段仅用于读取和维护老模块历史文件，新项目与全新模块禁止执行**。新模块的需求背景、角色权限概述与待确认清单已下沉到 §2.4 模块级 PRD；翻新模块只执行 §2.3-翻新。

**目标**：将口头描述、零散材料整理为可评审的结构化需求底稿。

**产物文件命名**（强制，遵循 `doc-format.mdc §"正式交付文档命名"`）：

- 模块级底稿：`docs/formal-requirements/M{n}-01-{模块名}结构化需求底稿.md`
- 翻新模式替代品：`docs/formal-requirements/M{n}-01-{模块名}模块老系统盘点与翻新决策.md`
- `{n}` 以 P07 §11 模块编号固定表为准；首个模块从 `M1` 起，新模块往后追加，不得插队回填。

**输出内容**：

- 背景与目标（为什么做这个模块）
- 用户角色与权限概述
- 核心功能点列表（不含详细规则）
- 主流程（文字描述，可含 Mermaid 流程图骨架）
- 异常流程与边界条件（初稿）
- 风险与依赖项
- **待确认清单**（第一版）

**生成时强制约束**：

- **四类区分（强制）**：必须明确区分"用户原话""真实需求""方案建议""待确认事项"四类，禁止混为一谈
- **去重归并**：对重复诉求做去重归并，输出统一表述，禁止重复罗列
- **冲突识别**：对互相矛盾的信息明确标出冲突点、冲突来源和处理建议（范围冲突/角色冲突/流程冲突/规则冲突分别识别）
- **不脑补**：对无法确认的信息必须标注"待确认"，禁止自行脑补业务事实
- 输入材料不足以进入 PRD 时，须在"下一步输出建议"中明确仍需补充哪些信息

**历史文件迁移约束**：

- 老模块底稿中的已确认事项须迁移或引用到 P07 §9~§12 与当前模块 PRD，底稿本身不再作为后续活动流程入口。
- 未确认事项统一迁移到模块 PRD §13 待确认清单；不得要求新模块先补一份底稿。

**项目级 PRD · 对齐决策段职责**：

P07 §9~§12 承担原独立项目对齐稿职责，须先于模块 PRD 完成：

- **统一术语口径**：锁定角色、状态、页面、业务对象和关键术语的最终命名（后续 PRD/SRS/原型不得擅自修改）
- **明确范围边界**：本期范围、非本期范围一次性确认
- **沉淀已确认决策**：将本期前已答复的待确认问题归入"已确认决策"表
- **作为后续 PRD 内容的直接输入**：完成的对齐决策段应能直接作为模块级 PRD 生成的依据

**对齐决策段生成时强制约束**：

- 完成后须用户对 §9 已确认决策表明确确认，**才能**进入模块级 PRD 阶段
- 未确认的事项一律标注"待确认"，禁止默认进入模块级 PRD



### 2.3-翻新 老系统盘点与翻新决策（翻新模式专用）

> **本子流程的边界**
>
> 本子流程只承担"老系统盘点 + 翻新决策"，产出翻新模式专用 M{n}-01。
> 完成本子流程后直接回到 §2.4 模块 PRD，再按 SRS → 流程图 → 原型推进；**禁止**在本子流程内重复 PRD/SRS/原型流程。



#### 触发条件（强匹配关键词）

满足以下任一条件即触发：

- 用户提及"翻新"、"老系统改造"、"老系统迁移"、"基于老系统重做"、"旧系统的 XX 模块迁过来"
- 用户提供老系统访问地址 + 账号
- 用户表达本模块在老系统已有实现，需要在新平台重做

如果用户描述的是**老系统不存在的新功能**，应回退到正常 §2.3 阶段一流程。

#### 核心原则

1. **不脑补**：所有翻新决策（保留/升级/废弃/新增）必须有理由，禁止凭空判断。
2. **盘点优先于决策**：先把老系统功能清单完整列出，再逐项做翻新决策。
3. **不绕过下游**：完成后必须明确移交主流程阶段二，禁止跨过对齐稿/PRD/SRS 直接做原型。
4. **凭证错误即停**：若 AI 用用户提供的凭证登录老系统失败，必须立刻在 chat 中向用户询问，禁止猜测或重试更换密码。
5. **决策需用户确认**：翻新决策表必须经用户在子流程检查点确认，才能移交下游。

| 老系统对应模块入口路径     | 强制      | 例如：项目档案 → `/projectAdd/show?id=3`    |
| 本期翻新范围（哪些子功能要做） | 强制      | 缺失时须追问                               |
| 本期明确不做（非本期）     | 推荐      | 与本期范围互斥                              |
| 盘点方式            | 强制      | A. AI 自动浏览 / B. 用户提供截图 / C. A+B 混合   |
| 已有截图或素材         | 视盘点方式而定 | 选 B 或 C 时必须提供                        |




#### 第二步：老系统盘点

按用户在 §第一步选定的盘点方式执行：

- **方式 A：AI 自动浏览** —— 使用浏览器自动化工具登录老系统、按用户指定入口路径打开页面，抓取字段 / 控件 / 按钮 / 状态值 / 流程节点。**禁止**未经用户同意自行尝试指定入口外的任意 URL。凭证错误立即停止并 chat 询问。
- **方式 B：用户提供截图** —— 用户提供老系统页面截图（建议：列表页 + 详情页 + 编辑/新增弹窗 + 异常态）。AI 基于截图整理字段/控件/按钮清单。截图看不清的信息必须在"待确认表"中标出。
- **方式 C：混合** —— AI 自动浏览作为主输入，用户截图作为补充。两者冲突时以 AI 实际浏览结果为准，并在"待确认表"中标记。

**盘点完成的判定**：必须填满老系统盘点模板的"功能清单表"≥ 5 项，否则视为盘点不充分。

#### 第三步：翻新决策（4 表强制）

按 `templates/requirements/legacy-system-renovation-template.md` 模板填写 4 张表：


| 表           | 内容                     | 强制约束                       |
| ----------- | ---------------------- | -------------------------- |
| 表 1 老系统功能清单 | 页面 / 字段 / 操作 / 截图源     | 至少 5 项；每项须含老系统截图链接或截图文件路径  |
| 表 2 翻新决策    | 每项标记：保留 / 升级 / 废弃 / 新增 | 每项必须填"决策理由"，禁止仅写"按需调整"等空话  |
| 表 3 术语映射    | 老系统命名 → 新系统命名          | 默认沿用老命名；改名项必须填"改名理由"       |
| 表 4 待业务决策   | 需用户拍板的翻新策略             | 与对齐稿"待业务决策"格式保持一致，便于后续直接迁移 |


**禁止**：4 张表中任何一张为空就声明"盘点完成"。

#### 第四步：用户决策检查点（强制停止）

完成 §第三步后，输出以下检查点并立即停止本次回复：

```
【老系统翻新盘点完成】{模块名}
交付物：docs/formal-requirements/M{n}-01-{模块名}模块老系统盘点与翻新决策.md
盘点方式：{A/B/C}
功能清单：{n} 项
翻新决策汇总：保留 {a} 项 / 升级 {b} 项 / 废弃 {c} 项 / 新增 {d} 项
待业务决策：{e} 项（见 §5 表 4）

🛑 请在 §3 翻新决策表上逐项确认决策理由,并在 §5 待业务决策表上回复每条决策。
确认后即可移交主流程 §2.4 模块 PRD 继续。
```



#### 第五步：移交主流程

用户在 §第四步确认后：

1. **明确告知用户**：本子流程已完成，下一步进入 §2.4 模块 PRD。
2. **传递交付物**：`docs/formal-requirements/M{n}-01-{模块名}模块老系统盘点与翻新决策.md` 作为模块 PRD §需求背景、§业务规则与 §待确认清单的输入；跨模块决策同步到 P07 §9~§12。
3. **回到主流程**：从 §2.4 开始，不重做产品发现或历史底稿。



#### 报告归档（强制）

归档位置 + 命名格式详见 `.cursor/rules/doc-format.mdc §"正式交付文档命名"`（条目：老系统盘点与翻新决策）+ §"交付物存储路径"（归档至 `docs/formal-requirements/`）。

#### 答复忠实执行核查（强制）

用户在 §第四步给出决策后，**必须**按 `.cursor/rules/answer-faithfulness.mdc` 全流程执行：

- 读取盘点文件 → 提取每条决策答复 → 解析方向 → 核查改动是否落实 → 偏差报告 → 追加核查标识 → 状态回写。
- 任一步骤违规，立即停止"已完成"声明并报告给用户。

### 2.4 阶段二：PRD（模块级二件套的核心入口）

**目标**：将业务诉求转化为正式产品需求文档；新模块下，模块级 PRD 同时承担原 M{n}-01 底稿的"需求背景 / 角色权限概述 / 待确认清单"职责。

**产物文件命名**（强制）：

- 项目级 PRD：`docs/formal-requirements/P07-{系统名}产品需求文档（PRD）.md`（与项目对齐稿合并后归位至 P07，原 P08 已废弃，详见 `doc-format.mdc`）
- 模块级 PRD：`docs/formal-requirements/M{n}-02-{模块名}模块产品需求文档（PRD）.md`

**前置条件**：

- 项目级 PRD 已完成（或对应模块在项目级 PRD §模块全景索引中已登记）。
- **翻新模块**：§2.3-翻新 子流程已闭环，"老系统盘点与翻新决策"文件已用户确认。
- **全新模块**：直接进入本阶段，关键待确认项随 PRD §"待确认清单"一并产出，业务方确认后回写。

**输出内容（新模块二件套强制章节）**：

- **§需求背景**（**二件套新增必填**）：嵌入原底稿的"为什么做这个模块 / 用户角色概述 / 主要业务诉求"，覆盖业务侧"做这件事的动因"
- **§范围说明**：本期范围 / 非本期范围
- **§角色与权限矩阵**
- **§功能范围与非功能需求**
- **§各功能点交互说明**（含字段、状态、操作按钮，业务侧粒度；技术细节归 SRS）
- **§业务规则摘要**
- **§验收标准**（业务级，技术 AC 归 SRS §10）
- **§待确认清单**（**二件套新增必填**）：嵌入原底稿的待确认项，业务方确认后回写

**术语核对**：在 PRD 草稿输出后，与 P07 §10 术语口径做一次一致性检查：角色名、状态名、字段名、模块名是否全程统一。

### 2.5 阶段三：SRS

**目标**：在 PRD 基础上补充字段规则、校验逻辑、权限细则、接口数据要求和完整验收标准。

**产物文件命名**（强制）：模块级 SRS 文件路径 `docs/formal-requirements/M{n}-03-{模块名}模块软件需求规格说明书（SRS）.md`（项目级不出 SRS，详见 `doc-format.mdc §"SRS 粒度说明"`）。

**前置条件**：PRD 已完成，主体功能范围和交互规则已确认。

**必须覆盖的内容**：

- `§5 功能规格`：每个功能点按五段式结构展开：
  1. `功能描述`（业务目标和角色）
  2. `页面与字段`（字段清单、类型、校验规则、placeholder）
  3. `处理逻辑`（前端行为与后端行为分开描述）
  4. `状态与规则`（枚举、状态机、业务规则）
  5. `异常处理`（校验失败、权限不足、数据异常的兜底）
- `§7 权限与安全要求`
- `§10 验收标准`（可验证的 AC 条目）

**字段命名锁定**：SRS 输出后，对本模块的字段名、状态名做一次"锁定确认"，后续原型和代码不得随意更改。

### 2.6 阶段四：流程图

**目标**：依据 PRD/SRS 沉淀主流程、异常流程的可视化表示。

**产物文件命名**（强制）：模块级流程说明文件路径 `docs/flow/M{n}-04-{模块名}模块流程说明.md`。

**输出**：Mermaid `flowchart TD` 图 + 文字流程说明 + 异常分支描述。

**节点命名**：用业务动作命名（如"提交申请""主管审批"），一节点一动作。

### 2.7 阶段五：页面原型

**目标**：依据 SRS 字段清单和交互规格搭建可评审的 Vue 原型页面。

**前置条件**：SRS 中的功能规格、字段、状态机已完成。

**原型要求**：

- 页面文件保存在 `src/views/{模块目录}/` 下。
- Mock 默认存放在 `src/mock/{模块目录}.js`，共享枚举放在 `src/mock/enums.js`；复杂模块可使用嵌套目录，单页数据可内联。具体组织和发现顺序以 `vue-ui-implementation.mdc §"Mock 组织与发现协议"` 为权威源。
- 严格遵循 `vue-ui-implementation.mdc` 全部规范（控件类型、布局、Toast 文案、表单校验、占位 placeholder 等）。
- 若有现有原型参照，同时对照原型与 SRS 字段清单搭建，**禁止**仿制其他模块整页换皮。
- 弹窗/抽屉操作优先，减少路由跳转。

**原型完成后**：

- 输出页面清单（页面名 → 对应 SRS 功能点 → 原型路径）
- **触发下游** `评审` **SKILL**：先走阶段 1 严格审查（多轮 R1→Rn 闭环至无 P1/P2）→ 闭环后自动衔接阶段 2 原型评审业务决策
