# 交付检查

## 上下游 SKILL（工作流定位）

本 SKILL 在项目工作流中处于**正式交付前的总收口检查**节点，是多份交付物对齐核验的最后关卡。

| 上游 | 本 SKILL | 下游 |
|------|---------|------|
| `项目与模块启动` / `评审`（阶段 1 + 阶段 2） / `接口对齐` / `文档生成与版本管理` / `需求变更`（任意阶段交付物完成后） | **交付检查**（一致性广度核验） | 正式交付 / 进入下一迭代 |

**与上游 `评审` SKILL 阶段 1（严格审查）的关系**：

- 阶段 1 严格审查负责**单模块深度核查**（文档/原型/代码三层 P1/P2/P3 编号问题）；
- 交付检查负责**多交付物广度核查**（PRD/SRS/流程图/原型/测试/说明书/阶段决策横向一致性）；
- 两者**互补**：典型场景是单模块严格审查闭环后，触发交付检查做跨多份交付物的横向核验。

**典型工作流**：

```
（多个模块各自完成 严格审查 + 原型评审）→ 交付检查（广度一致性核验）→ 正式交付
```

## 核心原则

1. 检查的目标是发现交付物之间的不一致、缺失项和阻断风险，不是直接重写整套文档。
2. 必须优先检查术语、角色、状态、字段、页面名称、按钮名称和范围边界是否一致。
3. 必须区分“阻断交付的问题”“非阻断问题”“待确认问题”。
4. 若项目当前仍处于原型评审阶段，不应默认要求完整正式交付包齐全，应按当前阶段目标检查。
5. 若用户未明确要求进入正式交付，不得把“可补齐项”写成“必交项”。
6. PM 阶段执行本检查时，以 P07、模块 PRD/SRS、原型、评审结论和开发交接包为范围，不要求接口对齐报告、数据库、生产构建、联调或部署结果。
7. 所有检查阶段必须排除 `docs/acceptance/` 与 A01～A03，不得读取、扫描、核查、修改或将其计入缺失项。

## 检查范围

优先检查以下交付物：

- 结构化需求底稿（**仅老模块兼容**；新模块走二件套）
- 项目级 PRD（合并版 P07，含原"项目对齐稿"职责）
- 模块级 PRD
- SRS（含业务规则）
- 流程图 / 流程说明
- 页面原型
- 测试用例
- 严格审查报告（按最新轮次 R{n} 引用，问题清单已统一由 `评审` SKILL 阶段 1 维护）
- 使用说明书
- 原型评审结论与阶段决策
- 一致性检查结果；构建结果仅在程序员正式交付前检查时纳入

**强制排除**：

- A01 需求规格说明书、A02 概要设计说明书、A03 详细设计说明书及 `docs/acceptance/` 下全部文件。
- 用户要求把 A01～A03 纳入交付检查时，本 SKILL 必须停止并说明其不属于项目建设交付范围；不得调用、路由、跳转或串联执行 `项目验收文档`。

如果部分交付物尚未生成：

1. 先判断这些交付物在当前阶段是否应存在。
2. 若当前阶段不要求，标记为“本阶段可不检查”。
3. 若当前阶段应存在但缺失，标记为“缺失项”。

## 检查流程

### 第一步：确认当前阶段与目标

先确认本轮检查属于哪一类：

- 页面原型可评审检查
- 正式文档可评审检查
- 正式交付前检查
- 需求变更后的影响收口检查

若目标不清晰，优先追问：

- 本轮目标是原型评审、文档评审还是正式交付
- 当前必须纳入检查的交付物有哪些
- 是否已有用户确认的最终交付清单

### 第二步：按一致性维度逐项核对

至少覆盖以下维度：

1. 术语一致性：同一业务对象、页面、状态、字段、按钮在各交付物中是否同名
2. 角色一致性：角色定义、权限口径、责任边界是否一致
3. 范围一致性：本期范围、非本期范围、待确认项是否一致
4. 流程一致性：主流程、异常流程、状态流转是否闭环
5. 原型一致性：页面结构、关键交互、空态、异常态、禁用态是否与文档一致
6. 测试映射一致性：测试用例是否覆盖关键流程、关键规则和异常场景
7. 说明书一致性：操作路径、角色说明、注意事项是否与原型和文档一致
8. 阶段决策一致性：当前阶段目标与已确认的后续动作是否一致

### 第三步：输出检查结论

默认将结果整理为以下类别：

- 阻断项
- 非阻断项
- 待确认项
- 缺失项

输出时优先写最影响交付的问题，再补充一般问题。

### 第四步：给出处理建议

对每个问题尽量补充：

- 影响交付物
- 建议修正方向
- 是否阻断进入下一阶段

如果问题集中在某一层，明确建议回到对应阶段处理，例如：

- 项目级术语和范围不一致：回到 P07 §9~§12；模块范围不一致：回到模块 PRD
- 规则和状态不一致：回到 SRS
- 流程与页面不一致：回到流程设计或页面原型
- 覆盖不完整：回到测试补充或说明书补充

## 输出要求

- 默认使用正式、准确、可评审的中文表达。
- 先给检查结论，再给问题明细和处理建议。
- 问题按严重程度排序，优先列阻断项。
- 若本轮未发现明显阻断项，应明确写“本轮未发现明显交付阻断项”，并说明剩余风险或可补强项。
- 对不确定内容统一标注“待确认”。
- 不得把“建议修正”写成“已修正完成”。

## 第五步：用户决策后的执行核查（强制）

用户对交付检查发现的"阻断项 / 非阻断项 / 待确认项 / 缺失项"给出"接受 / 拒绝 / 推迟"决策后，**必须**按 `.cursor/rules/answer-faithfulness.mdc` 全流程执行答复忠实执行核查：

- 读取本轮交付检查输出报告 → 提取用户答复 → 解析方向 → 核查实际改动是否针对每条问题落地 → 偏差报告 → 追加核查标识 → 状态回写。
- **强制状态回写**：在交付检查问题表中将每条状态从"待修复 / 待业务确认"更新为"✅ 已修复 / ✅ 已闭环 / 🟡 已推迟 / ❌ 不修复"；同步更新报告头部"总体评级"。
- 涉及多份交付物联动改动时，须 `Grep` 验证全项目术语 / 字段 / 状态命名统一性。

> **报告归档**：交付检查报告**默认作为对话输出，不强制归档**。如用户明确要求归档，**归档位置 + 命名格式**详见 `.cursor/rules/doc-format.mdc §"正式交付文档命名"（交付检查报告）+ §"交付物存储路径"`。
