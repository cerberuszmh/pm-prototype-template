# 项目总入口

## 核心职责

本 skill 不直接替代其他专项 skill，而是负责：

1. 判断当前任务属于哪个阶段
2. 判断当前目标属于哪类工作
3. 将任务分流到最合适的已有 skill
4. 在目标不清晰时，先追问关键问题

当前技能库存按**主责方与使用边界**分为 5 组；前 4 组参与默认分流，第 5 组仅显式触发：

### PM 主责（6 个，PM 直接触发并产出）

- `项目与模块启动`（项目级首次启动先经产品发现并生成 P07 合并版 PRD；模块级启动先按该 SKILL §1.4 选档：文档先行按 PRD→SRS→流程图→原型推进，双速轨按 快速轨→方向确认→正式轨 推进；**翻新场景**进入该 SKILL §2.3-翻新 子流程后回到模块 PRD）
- `产品发现`（**项目级一次性**，从模糊分散素材提炼出系统级需求地图 / JTBD / 用户旅程图 / 功能模块 / IA；仅项目级首次启动触发，模块级引用成果不重做）
- `需求变更`
- `评审`（强制两阶段：阶段 1 技术 QA 严格审查多轮 R1→Rn 闭环至无 P1/P2，阶段 2 业务原型评审拍板；触发词包含 /评审、/严格审查、/原型评审）
- `开发交接`（原型评审通过后向开发团队交付"AI 友好开发包"，本期默认只产出数据字典）
- `文档生成与版本管理`（原"文档生成或补充"，已合并版本升级能力）

### 跨边界（1 个，PM 或开发均可触发）

- `交付检查`（跨文档一致性核查；PM 评审前可用，开发交付前也可用）

### 面向开发（1 个，程序员主责，PM 仅在审核字段命名/枚举值时协助）

- `接口对齐`（前端 mock 字段 vs. 后端真实接口对比，联调准备）

### 基础设施（1 个，技术触发，不参与业务工作流）

- `启动项目`（启动 Vite 开发服务器，触发词："启动项目""跑起来""开发服务器"等；不影响业务流程，独立存在以便快速调起本地预览）

### 独立验收辅助（1 个，仅显式触发，不参与项目建设标准流程）

- `项目验收文档`（本处仅登记技能库存，不承担路由、跳转或调用；只有用户直接输入该技能定义的专用手动命令才可触发。按需生成 A01 需求规格说明书、A02 概要设计说明书和 A03 详细设计说明书；不进入默认分流、推荐工作流或阶段门槛，不计入 PM 交付物，也不作为程序员工作依据）

## 推荐完整工作流

```
PM 主责：项目与模块启动（项目级先经【产品发现】→ P07 合并版 PRD；模块级按档位二选一：A 文档先行 PRD → SRS → 流程图 → 原型，或 B 双速轨 快速轨（轻量摘要 → 草稿迭代）→ 方向确认 → 正式轨（反向 PRD → SRS → 正式原型））→ 评审【阶段 1 严格审查多轮 R1→Rn 闭环至无 P1/P2 → 阶段 2 原型评审业务拍板】→ 开发交接（PM 责任终点）
程序员主责：接口对齐 → 生产构建 → 联调 → 部署与正式交付
```

> **PM 交付边界**：PM 责任范围到【原型评审通过 + 开发交接产出】为止；PM 只需确认 `npm run dev` 可启动且关键原型流程可演示，`npm run build` 不属于 PM 原型交付门槛。【接口对齐】及之后阶段（生产构建、联调、部署、交付检查的开发侧执行）由程序员主责。【交付检查】属跨边界 SKILL，PM 在评审前也可主动触发用作一致性自检。
>
> **验收文档独立边界**：`项目验收文档` 不出现在上述流程箭头中。本 SKILL 及其分流逻辑不得调用、跳转或串联执行该技能，只能提示用户另行使用验收技能定义的专用手动命令。

- **评审 SKILL 的两阶段衔接**：阶段 1 严格审查负责发现技术问题（P1/P2/P3），阶段 2 原型评审负责业务侧阶段决策；阶段 2 "需修改项优先引用阶段 1 P/Q 编号"，避免双重维护问题。
- **变更可在任意节点插入**：触发 `需求变更` SKILL，并按变更影响重新触发上游环节。

## 第二步：若目标不清晰，先追问

当用户表达较宽泛时，优先补问以下 3 个问题中的必要项：

1. 本轮目标是到“方向确认”（仅双速轨档）/“原型评审”为止，还是继续完成“开发交接”（PM 责任终点）
2. 当前最想推进的是“原型 / 文档 / 变更 / 检查”哪一类
3. 当前已有材料有哪些：需求材料、PRD、SRS、流程图、原型、评审反馈、变更记录

如果问题能从上下文直接判断，则不要重复追问。

## 第三步：默认决策顺序

当同一请求同时包含多个方向时，默认按以下顺序判断：

1. 先识别是否属于需求变更
2. 再识别是否属于评审（含技术 QA 严格审查 + 业务原型评审两阶段，由 `评审` SKILL 内部分流）
3. 再识别是否属于交付检查
4. 再识别是否属于单一文档生成或版本管理
4b. 再识别是否属于开发交接（原型评审已通过 + 用户明确要做开发交付包，本期默认仅强制产出数据字典）
5. 如果仍是新项目或新模块宽泛需求：
   - **翻新场景**（用户提到老系统 / 翻新 / 迁移 / 老系统已有该模块）→ `项目与模块启动` SKILL §2.3-翻新 子流程，完成后回到模块 PRD
   - **全新场景** → `项目与模块启动`（**项目级首次启动**先经 `产品发现` 产出系统级成果，再生成 P07；模块级新增直接进入模块 PRD，引用已有产品发现成果与 P07）

这样做的原因：

- 变更会影响后续所有交付物，优先级最高
- 评审在进入下一阶段前强制执行（先技术 QA 再业务拍板）
- 交付检查通常发生在多份交付物都存在之后

## 第四步：阶段约束

总入口在分流时遵守的阶段约束以 `项目与模块启动` SKILL §核心原则为权威源，本 SKILL 不重复定义。核心要点：未完成需求清洗前不进入正式交付、用户未明确决策不进入下一阶段、不自动扩展为全套交付。

## 输出要求

- 默认先给出“我判断当前应走哪条路线”的简短结论。
- 若需要分流，明确说出建议使用的 skill 名称和原因。
- 若需要追问，问题尽量少且聚焦，不做大段铺陈。
- 若上下文足够清晰，可直接进入对应 skill 的执行方式，不必重复解释全套流程。

## 常用依据

- 全部子 SKILL：见 §核心职责列表，分为 5 组（PM 主责 6 / 跨边界 1 / 面向开发 1 / 基础设施 1 / 独立验收辅助 1，合计 10 个，不含本 SKILL 自身）；前 4 组参与默认分流，第 5 组仅显式触发。**SKILL 体系新增 / 删除时必须同步更新本节列表**，保持与 `.cursor/skills/` 目录一致，禁止保留"列表与实际不一致"的状态
- `.cursor/rules/answer-faithfulness.mdc`（通用答复忠实执行核查规则）
