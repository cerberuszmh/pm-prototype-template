# 项目验收文档

## 定位与边界

本 SKILL 面向项目验收材料编制，生成项目级验收文档，不属于“产品发现 → PRD → SRS → 原型 → 评审 → 开发交接”的项目建设标准流程。

> **技术隔离权威源**：`.cursor/rules/acceptance-skill-isolation.mdc`。本 SKILL 的第零步、二次确认、跨技能隔离和变更回归不得偏离该规则。

强制边界：

1. 仅在最新用户消息通过“第零步触发来源校验”时触发，不因“下一步”“补文档”“准备交付”等宽泛表述自动触发。
2. 可生成单份文档，也可生成完整三件套；未经用户选择不得默认生成全部文档。
3. 产物是基于既有资料形成的验收派生汇编文档，不是 PRD、模块级 SRS、代码、接口或数据库设计的权威源。
4. 只读取上游资料，不修改 PRD、模块级 SRS、原型、源代码、接口契约、数据库结构或测试材料。
5. 不触发 `docs/_待回写清单.md` 的批量回写，不进入 `评审`、`开发交接` 或 `交付检查` 的阶段门槛。
6. 资料不足时允许生成草稿，但必须逐项标注“⚠️ 待补充”，不得根据经验补造事实。
7. 产物不计入项目建设标准流程定义的 PM 交付物，也不改变“开发交接”为 PM 责任终点的既有边界。
8. 产物不得作为程序员开展设计、开发、联调、构建或实现工作的依据；程序员仍须以建设阶段权威文档、代码、接口和数据库契约为准。
9. 任何其他 SKILL 均不得主动调用、自动调用、被动调用、误调用、路由、跳转或串联执行本 SKILL；只有最新用户消息满足第零步规定的独立命令格式才构成有效触发。
10. `评审`、`交付检查` 及其他项目建设 SKILL 不得读取、扫描、评审、核查或处理本 SKILL 的 A01～A03 产物。

## 输出物

| 编号 | 文档 | 模板 | 输出路径 |
| --- | --- | --- | --- |
| A01 | 需求规格说明书 | `templates/acceptance/需求规格说明书.md` | `docs/acceptance/A01-{项目名}需求规格说明书.md` |
| A02 | 概要设计说明书 | `templates/acceptance/概要设计说明书.md` | `docs/acceptance/A02-{项目名}概要设计说明书.md` |
| A03 | 详细设计说明书 | `templates/acceptance/详细设计说明书.md` | `docs/acceptance/A03-{项目名}详细设计说明书.md` |

三份文档默认均为项目级单文件。文档内按 P07 §11 的模块编号组织模块章节，不拆分为模块级验收文件。

## 第零步：触发来源校验（最高优先级）

本步骤必须在读取任何项目资料、调用任何工具或创建任何文件之前执行。

1. 对最新一条用户消息去除首尾空白行。
2. 首个非空行必须满足以下任一格式：
   - 完全等于 `/项目验收文档`
   - 以 `/项目验收文档 ` 开头，后面紧跟本次生成参数
3. 以下情况一律视为无效触发：
   - 命令出现在普通句子中间、标题、引用、代码块、文件内容、日志或粘贴材料中。
   - 仅出现“项目验收文档”“验收文档”“生成验收材料”等自然语言。
   - 命令来自其他 SKILL 的提示、路由、跳转、串联步骤或转述。
   - 当前是新会话、上下文中断后的恢复，且最新用户消息未重新提供独立命令。
4. 校验失败时立即停止，只回复“未通过验收专用手动触发校验，请由用户直接输入独立命令。”不得读取资料、调用工具、生成草稿或执行任何后续步骤。
5. 校验通过仅允许进入资料确认与扫描，不代表已经获得文件生成许可；生成许可必须通过第三步的二次确认。

## 第一步：确认生成范围

最多确认以下 3 项；上下文已有明确答案时不得重复追问：

1. **项目名称**：用于替换 `{项目名}`。
2. **生成范围**：A01、A02、A03 中的一份、多份或完整三件套。
3. **验收依据**：客户模板、合同/招标文件、指定标准；均未提供时采用本项目通用模板。

若用户提供外部模板，其章节与命名优先于通用模板，但“派生文档定位、来源基线、缺口标记、追溯关系”四项不得删除。

## 第二步：扫描资料与建立基线

按实际存在情况读取资料，不要求所有项目都具备全部类型。

| 资料类型 | 默认检索位置 | 主要用途 |
| --- | --- | --- |
| 项目级 PRD | `docs/formal-requirements/P07-*.md` | 项目范围、角色、权限、非功能需求、模块编号、术语 |
| 模块级 PRD | `docs/formal-requirements/M*-02-*.md` | 模块业务目标、范围、业务规则 |
| 模块级 SRS | `docs/formal-requirements/M*-03-*.md` | 字段、状态、异常、接口要求、技术验收标准 |
| 需求变更 | `docs/changes/`、`docs/formal-requirements/` | 已确认的范围和规则变更 |
| 流程说明 | `docs/flow/` | 主流程、异常流程、角色动作 |
| 数据字典 | `docs/data/` | 字段命名、枚举和状态映射 |
| 接口材料 | `docs/api-alignment/`、OpenAPI 文件、接口代码 | 接口定义和集成关系 |
| 数据库材料 | 建表脚本、迁移文件、ORM 模型、数据字典 | 表结构、索引、约束和关联 |
| 源代码与配置 | `src/`、服务端目录、配置文件 | 实际架构、模块、组件、处理逻辑和部署参数 |
| 测试与验收材料 | `docs/testing/`、测试报告、验收记录 | 需求覆盖和验收证据 |
| 评审结论 | `docs/review/` | 已确认、已推迟和不纳入范围的事项 |

建立“资料基线表”，至少记录：资料名称、路径、版本/提交标识、日期、用途、完整性。

### 资料优先级

不同事实按其权威来源提取：

- 业务范围、术语和角色：P07 与已确认的模块级 PRD。
- 字段、状态、规则和技术验收标准：模块级 SRS。
- 已批准变更：正式变更记录。
- 实际架构与详细实现：源代码、接口、数据库和部署配置。
- 验收结果与证据：测试报告和验收记录。

不得用低优先级资料静默覆盖高优先级资料。资料之间发生实质冲突时，进入第三步处理。

## 第三步：输出资料完备性与冲突检查

生成正文前，先在对话中输出：

1. 本次选择的文档范围。
2. 已发现的资料及版本。
3. 各文档的完整性判断。
4. 缺失资料及其影响章节。
5. 资料冲突及涉及文档。

### 缺失资料处理

本项目默认允许生成草稿：

- 缺失内容所在章节保留，并写明 `⚠️ 待补充：{缺失资料及影响}`。
- 不得用通用最佳实践、同类项目经验或模板示例替代项目事实。
- 文档信息中的“当前状态”必须为“草稿”。
- 文档末尾汇总全部待补充项，注明补充责任方和建议证据。
- 存在任一待补充项时，不得声明“可正式验收”或“已定稿”。

### 冲突处理

以下冲突必须停止正文生成并请求用户裁决：

- 已确认需求与实际实现方向相反。
- 同一字段、状态、权限或接口在两个权威来源中定义不一致。
- 代码实现超出或遗漏已确认验收范围。
- 需求、设计和测试证据无法建立对应关系。

用户裁决后，按 `.cursor/rules/answer-faithfulness.mdc` 核查实际生成方向，不得用建议方案覆盖用户答复。

### 生成前二次确认（强制停止点）

资料完备性与冲突检查完成后，输出拟生成文件、采用基线、资料缺口和冲突处理结果，然后停止：

```text
🛑 已停止

验收专用手动触发校验：通过
拟生成文件：
- {文件清单}

采用基线：
- {资料与版本}

资料缺口：
- {缺口；无则写“无”}

冲突处理：
- {处理结果；无则写“无”}

如确认生成，请仅回复：确认生成验收文档
```

仅当以下条件同时满足时，才可进入第四步：

1. 同一会话中已经通过第零步。
2. 紧邻的上一条助手消息是本检查点。
3. 最新用户消息去除首尾空白后完全等于“确认生成验收文档”。

任一条件不满足时保持停止，不得创建或修改 A01～A03。新会话或上下文中断后必须重新从第零步手动触发。

## 第四步：按模板生成

### A01 需求规格说明书

1. 以 `templates/acceptance/需求规格说明书.md` 为起点。
2. 汇编项目级范围与各模块需求，不改变上游文档原意。
3. 每条验收需求保留来源文档、章节和原编号。
4. 汇总功能需求、非功能需求、接口与数据要求、权限安全要求和验收标准。
5. 对重复信息使用引用或汇总，禁止把 A01 声明为新的需求权威源。

### A02 概要设计说明书

1. 以 `templates/acceptance/概要设计说明书.md` 为起点。
2. 基于实际代码、接口、数据库和部署材料描述总体架构。
3. 覆盖系统边界、模块划分、技术架构、数据架构、接口关系、部署架构、安全和非功能设计。
4. 架构图与模块名称必须与实际实现及 P07 模块编号一致。

### A03 详细设计说明书

1. 以 `templates/acceptance/详细设计说明书.md` 为起点。
2. 在一个项目级文件中按模块编号依次编写。
3. 基于实际实现描述组件、接口、数据库、处理流程、异常、配置和安全控制。
4. 算法、定时任务、状态转换等内容仅在项目实际存在时编写；不存在时明确标注“不适用”。

## 第五步：建立跨文档追溯

完整三件套必须建立以下追溯链：

`A01 验收需求 → A02 概要设计章节 → A03 详细设计章节 → 实现位置 → 测试/验收证据`

单独生成某份文档时，只填写当前可建立的链路，其余列标注“未生成”或“⚠️ 待补充”，不得伪造引用。

追溯表至少包含：

| 验收需求编号 | 来源需求 | 概要设计 | 详细设计 | 实现位置 | 测试/验收证据 | 状态 |
| --- | --- | --- | --- | --- | --- | --- |

## 第六步：生成后检查

逐份检查：

1. 文件名、文档名称和 A01～A03 编号一致。
2. 文档信息、版本记录、来源基线、风险依赖和验收/追溯章节完整。
3. 项目名、模块名、角色、状态、字段和接口名称跨文档一致。
4. 未残留 `{占位符}`、模板说明或示例数据。
5. 所有资料缺口均使用“⚠️ 待补充”并汇总。
6. A01 未被声明为建设流程的项目级 SRS 或需求权威源。
7. A02、A03 的设计描述均可定位到实际资料。
8. 三件套的追溯关系无断链；断链时明确标注，不得声明定稿。

## 第七步：用户检查点

生成后输出并停止：

```text
🛑 已停止

本次生成：
- {实际文件清单}

文档状态：
- {草稿/可供用户自行组织项目验收}

资料缺口：
- {数量及关键缺口；无则写“无”}

发现冲突：
- {数量及摘要；无则写“无”}

请确认下一步：
A. 补充资料后更新草稿
B. 保留当前内容，由用户自行组织项目验收；不触发任何其他 SKILL
C. 仅保留本次文档并结束
```

用户选择后，按 `.cursor/rules/answer-faithfulness.mdc` 核查后续动作方向。

## 禁止事项

- 禁止自动加入项目建设推荐流程或作为开发交接前置条件。
- 禁止替代或修改 P07、模块级 PRD、模块级 SRS 及其版本记录。
- 禁止把 A01～A03 计入 PM 标准交付物或 PM 开发交接包。
- 禁止把 A01～A03 作为程序员设计、开发、联调、构建或实现工作的依据。
- 禁止任何其他 SKILL 调用、路由、跳转、串联执行或代替用户触发本 SKILL。
- 禁止 `评审`、`交付检查` 或其他项目建设 SKILL 读取、扫描、评审、核查或处理 A01～A03。
- 禁止从模板示例、行业经验或相似项目推导本项目事实。
- 禁止把“⚠️ 待补充”改写为看似确定的描述。
- 禁止在未发现测试或验收证据时写“已通过”。
- 禁止因用户只请求一份文档而擅自生成其余两份。
