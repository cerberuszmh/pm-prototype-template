# 接口对齐

## 上下游 SKILL（工作流定位）

本 SKILL 在项目工作流中处于**前后端联调准备**节点，是原型评审通过后、构建验证前的桥梁。

| 上游 | 本 SKILL | 下游 |
|------|---------|------|
| `开发交接`（数据字典等开发包已就绪） | **接口对齐**（mock vs 真实接口字段对照） | 本 SKILL「构建验证移交清单」（真实联调）→ `交付检查` |

**典型工作流**：

```
原型评审通过 → 开发交接（数据字典等）→ 接口对齐（生成字段差异报告）→ 后端联调 → 本 SKILL 构建验证移交清单 → 交付检查 → 正式交付
```

> **数据字典作为对齐输入**：本 SKILL 在执行字段对齐时，应优先以 `docs/data/{模块名}数据字典.md` 为前端字段命名权威源（已包含中文 ↔ 前端 ↔ 后端三栏映射），SRS §5 仍是字段语义权威源。

## 核心原则

1. **mock 是现状，SRS 是规范，接口是目标**：先以 SRS 字段清单为准，再对照 mock 实现，最后输出接口契约建议。
2. **区分三类字段**：
   - **纯后端字段**：由后端生成和维护，前端只读（编号、建档日期、状态变更时间等）
   - **前后端共有字段**：前端展示，后端存储（名称、类型、面积等业务字段）
   - **纯前端字段**：仅用于 UI 渲染，不需要后端返回（如 `statusColor`、`typeLabel` 等枚举展示文字）
3. **字段命名规范**：前端 camelCase，后端 snake_case，输出时给出双侧命名对照。
4. **不编造接口实现**：后端框架、认证方式、分页格式等按项目已有约定，不确定的标注"待确认"。

## 第一步：确认对齐范围

追问或从上下文判断：

- 对齐哪个模块？（根据项目实际模块名称确认）
- 是全量对齐还是只对齐某个接口类型（列表/详情/新增/编辑/删除/状态变更）
- 是否已有后端接口文档或字段定义？（若有，请提供；若无，则以 SRS 为准生成建议稿）

---

## 第二步：读取 mock 数据

mock 数据有两种存放方式，**两种都须支持识别**：

### 方式 A：独立 mock 文件（推荐用于复杂模块）

| 模块 | mock 文件路径 |
| --- | --- |
| {模块名称} | `src/mock/{模块目录}/{模块名}.js`（路径以项目实际结构为准） |

### 方式 B：组件内联 reactive 数组（适用于结构简单、单页消费的模块）

mock 数据直接定义在 `src/views/{模块目录}/*.vue` 组件 `<script setup>` 块内，例如：

```js
// src/views/example/SamplePageOneView.vue
const mockRecords = reactive([
  { id: 1, code: "X00001", name: "...", ... },
  ...
]);
```

**识别步骤**：

1. 用 `Glob` 找到 `src/views/{模块目录}/*.vue`；
2. 用 `Grep` 搜索 `reactive\(\[` 模式定位 mock 数组起始；
3. 用 `Read` 读取 mock 数组所在行范围；
4. 提取每条记录的字段名、类型、示例值。

### 从 mock 数据中识别（两种方式通用）

1. **实体结构**：每个 reactive 数组中的对象结构（字段名、类型、示例值）
2. **计算字段**：`computed()` 中生成的派生字段（如 `summaryNature`、`greenhouseOptions`）
3. **枚举映射**：`OPTIONS` 常量中 `value ↔ label` 对应关系（含 `proTypeOpts`、`statusColorMap` 等）
4. **辅助函数**：`nextGreenhouseId()`、`nextPlotId()`、`formatNum()` 等由前端模拟的编号生成或格式化逻辑

---

## 第三步：对照 SRS 字段清单

读取对应模块 SRS 的字段表（§5.x.2 页面与字段），逐字段比对：

| 检查项 | 说明 |
| --- | --- |
| 字段覆盖率 | mock 中是否包含 SRS 定义的全部字段 |
| 字段名一致性 | mock 字段名与 SRS 字段名是否一致 |
| 类型一致性 | 数据类型（字符串/数值/日期/枚举/数组）是否与规格吻合 |
| 规则覆盖 | SRS 中的业务规则是否在 mock 数据中有体现 |
| 多余字段 | mock 中存在但 SRS 未定义的字段（可能是遗漏规格或前端私有字段） |

---

## 第四步：生成接口对齐报告

输出以下结构的 Markdown 报告：

### 4.1 实体字段对照表

每个接口实体输出一张表：

| 前端字段（camelCase） | 后端字段（snake_case建议） | 类型 | 字段归属 | 说明 |
| --- | --- | --- | --- | --- |
| `id` | `greenhouse_id` | string | 后端生成 | 格式 GH-{乡镇码}-{三位序号} |
| `statusColor` | — | string | 纯前端 | 由 statusValue 枚举映射，无需后端返回 |
| `typeLabel` | — | string | 纯前端 | 由 type 枚举映射，前端自行转换 |
| ... | ... | ... | ... | ... |

字段归属标注规则：
- `后端生成`：后端维护，前端只读
- `前后端共有`：前端编辑，后端存储
- `纯前端`：前端渲染用，不进入接口
- `待确认`：归属不明确，需与后端协商

### 4.2 接口清单建议

按 CRUD 列出建议接口，包含：

- 接口路径（RESTful 风格）
- 请求方法
- 关键请求参数（含分页、筛选）
- 关键响应字段
- 说明与待确认项

示例（以"项目档案"模块为例，实际路径以项目约定为准）：
```
GET    /api/projects          # 列表查询（含分页、筛选）
POST   /api/projects          # 新增档案
GET    /api/projects/{id}     # 详情查询
PUT    /api/projects/{id}     # 编辑信息
PATCH  /api/projects/{id}/status  # 单独状态变更（防竞态）
DELETE /api/projects/{id}     # 删除档案
```

### 4.3 枚举标准化建议

列出需要前后端约定的枚举值（value 及其 label 对照），避免各自维护产生漂移。

### 4.4 编号生成逻辑迁移说明

说明当前由前端模拟的编号生成（如 `nextGreenhouseId()`）在后端接入后应由何处承担，以及迁移要点。

### 4.5 待确认清单

列出所有标注"待确认"的事项，供后端联调时核对。

---

## 第五步：输出建议

报告**归档位置 + 命名格式**详见 `.cursor/rules/doc-format.mdc §"正式交付文档命名"（接口对齐报告）+ §"交付物存储路径"`。

**接口对齐特定的归档要求**：

- 报告内部标题可附日期：`{模块名称}接口对齐报告（{日期}）`
- 若 `docs/api-alignment/` 目录不存在，执行前用 `New-Item -ItemType Directory -Force -Path "docs/api-alignment"` 先创建
- 若同时对齐多个模块，每个模块单独一份报告

## 构建验证移交清单（接口对齐完成后执行）

> 本环节发生在 PM 已完成原型评审与开发交接之后，由程序员主责，不新增独立 SKILL，也不得反向作为 PM 原型交付门槛。接口对齐报告中的阻断差异与字段归属待确认项闭环后，按本清单执行；未接入真实后端时只能标记为“原型构建验证”，不得写成“联调通过”。

1. **生产构建**：在项目根目录执行 `npm run build`，命令退出码必须为 0。
2. **产物预览**：执行 `npm run preview`，使用命令输出的实际地址访问构建产物。
3. **关键冒烟**：至少验证系统首页、目标模块入口、列表查询、新增/编辑、状态变更和 404 兜底；涉及真实接口时同时验证成功、空数据、接口失败三种响应。
4. **结果记录**：记录 Node/npm 版本、构建命令与退出码、预览地址、冒烟结果、失败项和处理人。
5. **进入下游门槛**：生产构建及关键冒烟全部通过后才可进入 `交付检查`；任一失败立即停止，回到对应代码或接口问题修复。

---

## 第六步：用户决策后的执行核查（强制）

用户对接口对齐方案、字段归属决策（含"待确认"项的业务方答复、命名规范、字段映射调整等）给出答复后，**必须**按 `.cursor/rules/answer-faithfulness.mdc` 全流程执行答复忠实执行核查：

- 读取本轮接口对齐报告 → 提取用户答复（特别是 §4.5 待确认清单的回填）→ 解析方向 → 核查实际改动是否同步到代码 / mock / 字段对照表 → 偏差报告 → 追加核查标识 → 状态回写。
- **强制状态回写**：在 §4.1 实体字段对照表中将"待确认"列更新为明确归属（后端生成 / 前后端共有 / 纯前端）；在 §4.5 待确认清单中将每条"待确认"标注为"✅ 已确认（业务答复）"或"🟡 已推迟"。
- 涉及代码改动时（如字段重命名），须 `Grep` 验证全项目一致性。

---
